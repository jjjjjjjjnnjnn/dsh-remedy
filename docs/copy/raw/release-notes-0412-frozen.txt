## dsh-remedy 0.4.12

### Fixed

- **P-0041 — the installed CLI was silent on Linux, and exited 0.** `./node_modules/.bin/dsh-remedy verify`
  printed nothing and exited 0 on Linux and macOS while `node dist/cli.js verify` printed every fixture. The
  entry guard compared `import.meta.url` (the resolved file) with `pathToFileURL(process.argv[1])` (what the
  caller named), and npm installs a POSIX `bin` as a symlink, so the two differ and `main()` never ran. Both
  sides are realpath'd now. Windows installs a `.cmd` shim that passes the real path, which is why
  0.1.0–0.4.11 never saw it. `0.4.11` carries the old guard; install `0.4.12` to get the fix.
- **P-0040 — the acceptance recorder owned a fixture count the package owns.** The cold-directory install of
  `0.4.11` printed eight `PASS` lines and `OK 8 fixture(s)` with three zero exit codes, and the recorder wrote
  `ok: false` because it looked for the literal `OK 6 fixture(s)`. The count is derived from
  `data/fixtures/toolcall-fusion/*.json` and judged by `scripts/lib/acceptance.mjs`.

### Added

- Two tests that pin the shapes this release repairs: `tests/unit/acceptance.test.ts` judges the
  acceptance output against the repository's own fixture count, and `tests/unit/cli-entry.test.ts`
  asserts the installed `bin` shape (a symlink) and the direct path through the same guard.

### Changed

- `record_install_acceptance.mjs` no longer owns a fixture count: it counts
  `data/fixtures/toolcall-fusion/*.json` and judges with `scripts/lib/acceptance.mjs`, so adding a
  canonical fixture can never turn a green install into a recorded failure again.
- The market index names the two new releases and their measured publish timestamps, and its
  governance rule now follows the newest entry instead of the number that happened to be newest when
  the rule was written.
